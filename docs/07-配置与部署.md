## 0. 一句话

Python 3.12 + `uv sync` + `.env` + `data/*.json`，一条命令前台跑起来：**没有 Web 服务、没有任务队列**，断电风险靠 JSON 原子写兜。README 只保留一句话入口，安装 / 配置 / 启动 / 测试 / 部署的完整步骤都在本文。

## 1. 环境要求

| 项 | 要求 | 说明 |
|---|---|---|
| Python | **3.12+** | `pyproject.toml` 的 `requires-python = ">=3.12"`；仓库带 `uv.lock` |
| 包管理 | 推荐 [uv](https://docs.astral.sh/uv/) | 没有 uv 也能用 `venv + pip`，见 §2 |
| 网络 | 能直连 `api.telegram.org` 与 `linpx.ink` | 抓 Linpx 用 aiohttp，**不读 `HTTP(S)_PROXY`**；只有 Telegram 侧（httpx）会读代理变量。部署前先 `curl https://linpx.ink/` 确认直连可用 |
| Bot 身份 | 一个 Bot Token | 从 [@BotFather](https://t.me/BotFather) 申请 |
| 频道 | 分享 / 审核各需要频道，且 **Bot 必须是频道管理员** | 权限不足时表现为「发不出去」，日志里有 Telegram 报错 |
| 磁盘 | `data/`（KB~MB 级 JSON）+ `files/work/`（临时文件） | 交付后删除；启动时清空，进程被强杀留下的 `dl-*` 目录随下次启动回收 |

## 2. 安装

### 2.1 用 uv（推荐）

```powershell
git clone https://github.com/<owner>/FurryReadingBot.git
cd FurryReadingBot
uv sync
Copy-Item .env.example .env
```

```bash
git clone https://github.com/<owner>/FurryReadingBot.git
cd FurryReadingBot
uv sync
cp .env.example .env
```

`<owner>` 换成实际仓库地址。`uv sync` 会按 `uv.lock` 建好 `.venv/`，后面所有命令都跑 `.venv` 里的解释器；`.env` 至少填 `BOT_TOKEN` 与 `TEST_CHANNEL`（见 §4.1）。

### 2.2 不用 uv

仓库**没有** `requirements.txt`，依赖清单以 `pyproject.toml` 为准：

```powershell
python -m venv .venv
.venv\Scripts\python.exe -m pip install -U pip
.venv\Scripts\python.exe -m pip install "python-telegram-bot>=22.8" "aiohttp>=3.14.5" "aiofiles>=25.1.0" "pyzipper>=0.4.0" "requests>=2.34.2" "python-dotenv>=1.2.4"
```

> `pytest` 在 `pyproject.toml` 的 `[dependency-groups].dev` 里（运行时不需要）；要跑测试再单独 `.venv\Scripts\python.exe -m pip install pytest`。

## 3. 数据目录

| 路径 | 是什么 | 要不要提交 |
|---|---|---|
| `data/*.json` | 运行时状态：名单、兽人作者申请、作者下架申请、`file_id` 缓存、分享记录、未识别标签（`unknown_tags.json`，首次遇到未识别写法时自动建） | **不要**。根仓库 `.gitignore` 里有 `data/*.json` |
| `data/tags.toml` | 标签词表（词表源文件，见 [08](08-标签词表.md)） | **不要**。改完在数据目录提交；`/sync` 只提交 `*.json`，不会带上它 |
| `data.example/` | 模板：6 份 JSON + `tags.toml`（标签词表样例）。`furry_authors.json` 含一份公开的**兽人作者名单**；其余 JSON 是空结构（`black_request.json` 模板里没有，首次运行会自动建） | 可以，它是模板 |
| `files/work/` | 下载打包目录，交付后删除 | **不要**，已 gitignore |

> `sync_data.sh` / `sync_data.ps1` **不在 `data/` 里**：它们和 Bot 代码一起放在 `script/`（根仓库跟踪）。`data/` 保持纯数据，换机器时把数据目录一起带走即可；脚本只有一份，不会出现两个版本对不上的问题。

首次运行时的行为：

- 任何缺失的 JSON 会被 `JsonStore` **自动创建**为空结构（`storage/json_store.py`），所以 `test` 模式下只填 `BOT_TOKEN` + `TEST_CHANNEL` 也能启动，只是所有作者都不在名单里 → 全部走「申请」。
- 想让 Bot 开箱可用，把模板拷进 `data/`（JSON + `tags.toml`，别带 `data.example/.idea/` 那份历史残留）：

```powershell
New-Item -ItemType Directory -Force -Path data | Out-Null
Copy-Item data.example\*.json,data.example\tags.toml data\
```

```bash
mkdir -p data && cp data.example/*.json data.example/tags.toml data/
```

`data/` 目录只放运行数据；名单的备份 / 同步在 `data/` 单独操作。Bot 的 `/sync` 在 Linux 上执行 `script/sync_data.sh`、在 Windows 上执行内容等价的 `script/sync_data.ps1`；两个脚本按自身位置找 `../data`，所以定时任务里也要写 `script/` 下的路径。

## 4. 配置项（`.env` + `config.py` 常量）

`.env` 只放**部署相关**的 Token 与频道 ID；评分阈值、分享冷却、文件缓存 TTL、update 并发数是 `config.py` 里的**代码常量**，跟着代码同步，不需要在仓库里再配密钥。

从 `.env.example` 复制后填。`config.py` 用 `python-dotenv` + `os.environ` 读取，启动时由 `config_errors()` 检查必需项，缺失直接 `SystemExit` 并列出问题。

| 变量 | 必填 | 默认 | 作用 |
|---|---|---|---|
| `BOT_TOKEN` | ✅ | — | Bot Token。**缺失时进程直接 `SystemExit`** |
| `TEST_CHANNEL` | `test` 必填 | 空 | `SHARE_MODE=test` 时唯一的分享目标；也是 `TRANSIT_CHANNEL` 的回退值 |
| `TRANSIT_CHANNEL` | 可选 | `TEST_CHANNEL` | 待审申请（兽人作者申请、作者下架申请）的中转频道；未配置时一律复用 `TEST_CHANNEL` |
| `FURRY_READING` | `prod` 必填 | 空 | 兽人阅读频道；`prod` 下评分达标时同时发这里；也是分享文案里的「支持频道」 |
| `FURRY_NOVELS` | `prod` 必填 | 空 | 兽人小说频道；`prod` 下所有分享都发这里 |
| `FURRY_READING_NEW_GROUP` / `TEST_GROUP` | 可选 | 空 | `config.py` 会读，但**没有任何业务代码使用**，配了也不生效 |

**行为参数（`config.py` 常量，不在 `.env`）**

这些不是密钥，也不通过环境变量读取；改 `config.py` 后提交、重新部署即生效。

| 常量 | 当前值 | 作用 |
|---|---|---|
| `SHARE_MODE` | `prod` | `test` 只发 `TEST_CHANNEL`；`prod` 按评分分流到正式频道。只能是 `test` / `prod`，其他值启动失败 |
| `SHARE_SCORE_THRESHOLD` | `6` | `prod` 下同时发 `FURRY_READING` 的评分下限（评分在下载时算好、随 `file_id` 写进缓存） |
| `SHARE_COOLDOWN_DAYS` | `3` | 同一作品重复分享的冷却天数 |
| `FILE_CACHE_TTL_DAYS` | `7` | `file_id` 缓存有效期；命中就直接复用，不再上传 |
| `CONCURRENT_UPDATES` | `8` | update 并发数；必须是正整数（`0` / 负数会让 PTB 在建 `Application` 时抛 `ValueError`），`1` = 串行 |

关于默认值的三个坑：

1. `SHARE_COOLDOWN_DAYS` / `FILE_CACHE_TTL_DAYS` 是 `config.py` 常量（3 / 7）；`storage/` 里的 7 / 30 天只是直接构造 `ShareRecordStore()` / `FileCacheStore()` 时的兜底，Bot 运行时不会用到。
2. `TRANSIT_CHANNEL` 未配置时**任何模式**都会回落到 `TEST_CHANNEL`；`config_errors()` 里 `prod` 仍把它列为必填，但因为有回退，只有 `TEST_CHANNEL` 也为空时才会报错。
3. 启动校验只检查「有没有填」：填错的频道 ID 不会立刻报错，直到真正发消息才失败。

频道既可以填数字 ID（`-1001234567890`），也可以填公开频道的 `@username` —— 都是原样交给 Telegram API。

### 4.1 最小可运行

`SHARE_MODE` 是代码常量（当前 `prod`），所以最小配置也要覆盖 `prod` 的两条分流频道：

```dotenv
BOT_TOKEN=123456:AA...
FURRY_NOVELS=@furry_novels
FURRY_READING=-1001234567891
```

只填 `BOT_TOKEN` + `TEST_CHANNEL` 会启动失败（`config_errors()` 会列出缺 `FURRY_NOVELS` / `FURRY_READING`）。想在本地只往测试频道发，先把 `config.py` 的 `SHARE_MODE` 改成 `"test"` 再这样配：

```dotenv
BOT_TOKEN=123456:AA...
TEST_CHANNEL=-1001234567890
```

此时分享只发 `TEST_CHANNEL`，审核也用 `TEST_CHANNEL`。

### 4.2 生产形态

```dotenv
BOT_TOKEN=123456:AA...
FURRY_NOVELS=@furry_novels
FURRY_READING=-1001234567891
TRANSIT_CHANNEL=-1001234567892
```

> `prod` 下作品下载时按 `read_count` / `like_count` 算推荐指数并写进 `files_cache.json`；分享时 `score >= SHARE_SCORE_THRESHOLD` 会同时发 `FURRY_READING`，否则只发 `FURRY_NOVELS`。txt 分享一定有评分（作者整包没有统计，按低分处理）。规则见 [01 §1](01-功能清单与缺口.md) 与 `policy/scoring.py`。

## 5. 启动

```powershell
.venv\Scripts\python.exe bot.py
```

```bash
.venv/bin/python bot.py
```

- 日志走 stdout（`logging.basicConfig`，INFO 级）；`Bot 启动中……` 之后进入 **long polling**。
- `drop_pending_updates=False`：停机期间的消息会在重启后补处理。
- 并发：`Application.builder().concurrent_updates(CONCURRENT_UPDATES)` 并行处理 update；数值是 `config.py` 常量（默认 8，`1` = 串行），改代码后重新部署生效。不要用 `True`（PTB 里等于 256 路）。
- `post_shutdown` 通过 builder 注册（v20+ 里它不是 setter），退出时关掉复用的 aiohttp 会话。
- 同一链接的下载由 `DownloadService` 内的 `asyncio.Lock` 串行：第二次请求会等第一次传完并直接复用 `file_id`，不会重复抓取 / 上传；每次打包都在独立工作目录，不同作品仍并行。
- `/sync` 分两步：① `services/import_author_service.py` 先调 `sources/linpx/client.get_fav_users()` 抓 `https://api.linpx.ink/fav/user/cache`，把作者并入 `data/furry_authors.json`（note = `Linpx`；已收录 / 黑名单作者跳过）；② `services/sync_service.py` 执行同步脚本（超时 300 秒）把结果提交。Linux 用 `/bin/bash script/sync_data.sh`，Windows 用 `powershell.exe -NoProfile -ExecutionPolicy Bypass -File script/sync_data.ps1`。两个脚本**契约一致**（退出码 0/2/3/4/5、锁文件、跳过与提交文案），实现按平台各自最优（`.sh` 用 `flock -w 60`，`.ps1` 用「独占打开文件」）；**定时任务与 `/sync` 会排队执行**，不会同时 `git commit / pull --rebase / push`；Bot 侧再加一把进程内锁，连点 `/sync` 也不会拉起多个脚本。
- 推荐作者抓取走 `infra.http.get_json`：单次 30 秒超时、最多 3 次重试（1s / 2s 退避），最坏约 90 秒；这段不计入脚本的 300 秒预算，期间 Telegram 侧只看到「⏳」。
- 提交范围：脚本只 `git add -- ':(glob)*.json'`，即 `data/*.json`（**不递归子目录**）；`data/eval/`、`README.md` 等不会被 `/sync` 顺带提交，没有 JSON 变动就直接跳过。
- 提交身份：脚本用 `git -c user.name=… -c user.email=…` 只给本次提交用 bot 身份，**不会写进 `data/.git/config`**；你之后在 `data/` 里手动 `git commit` 仍是自己的身份。若仓库里残留过旧脚本写死的 bot 身份，手动清一次：`git -C data config --local --unset-all user.name`、`git -C data config --local --unset-all user.email`。
- 服务器定时任务只调 `script/sync_data.sh`，不经过 Bot、不联网抓推荐作者；推荐作者只在手动 `/sync` 时合并。抓取失败（接口 5xx / 超时）不会阻止提交，回复里会单独提示「Linpx 推荐作者抓取失败」；接口 404 或返回空列表按「0 个推荐作者」处理。
- **从旧部署迁移**：脚本已从 `data/` 移到 `script/`，crontab / 计划任务里的路径要同步改（`.../FurryReadingBot/data/sync_data.sh` → `.../FurryReadingBot/script/sync_data.sh`）；旧路径会直接找不到文件。仓库现在自带 systemd timer（见 §8.2），可以删掉旧的 crontab 行。数据仓库不再需要保留这两份脚本，删掉即可。
- 超时处理：先 `taskkill /F /T` 杀掉整棵进程树（Windows 上只杀 powershell 会留下握着仓库锁的 `git`），再最多等 5 秒回收已产生的输出。**不要**在超时后再调 `communicate()`——Windows 上被取消过的那次调用会永远等不到 EOF，`/sync` 会一直卡在锁上。
- Windows 上跑 `/sync` 的前提：系统自带的 `powershell.exe` + 已对私有数据仓库配好 git 凭据。脚本会设置 `GIT_TERMINAL_PROMPT=0` / `GCM_INTERACTIVE=never`，凭据缺失时直接失败并回显，不会停下来等输入。
- `/sync` 与 `/review` 共用一套权限：仅中转频道 `creator` / `administrator` 可用（`AdminPolicy`，默认拒绝；成员状态缓存 60 秒，撤权最多延迟一分钟）。非管理员只会收到「⚠️ 仅中转频道管理员可以同步运营数据」，不会触发脚本。`TRANSIT_CHANNEL` 与 `TEST_CHANNEL` 都未配置时没人能通过校验。
- 不启动轮询、只验证装配：

```powershell
.venv\Scripts\python.exe -c "import bot; print('import ok')"
```

### 5.1 上线自检清单

| # | 检查 | 不满足时的现象 |
|---|---|---|
| 1 | `.env` 里 `BOT_TOKEN` 有效 | 无效 Token 在 `run_polling` 阶段抛 `Unauthorized` |
| 2 | Bot 已加入所有频道并设为管理员 | 分享 / 中转消息发不出去，日志里 `Forbidden` / `chat not found` |
| 3 | 中转频道建议设为**私有** | 管理员判定看该频道的成员身份，私有能少一堆误触 |
| 4 | `data/furry_authors.json` 非空 | 空名单 → 所有作者都要走申请 |
| 5 | `files/work/` 可写、磁盘有余量 | 抓取 / 保存失败 |
| 6 | 服务器能直连 `linpx.ink` | 下载提示抓取失败，日志里 `异步请求 JSON 失败` |

## 8. 部署

### 8.1 现状

- 单进程、long polling、前台运行；重启只会丢内存里的 `_inflight`（分享并发保护）和下载串行锁，业务数据都在 JSON 里。
- 仓库 `deploy/` 里有三份参考 unit：bot 的 `furryreadingbot.service`、数据同步的 `furryreadingbot-sync.service` + `furryreadingbot-sync.timer`；**没有** Dockerfile、健康检查 / 指标（见 [01 §2 P2](01-功能清单与缺口.md)）。
- 想上线，最省事的是「一台机器 + 进程守护」。下面这份 unit 与 `deploy/furryreadingbot.service` 内容一致，路径 / 用户按实际部署改：

```ini
[Unit]
Description=FurryReadingBot
After=network-online.target

[Service]
Type=simple
WorkingDirectory=/opt/FurryReadingBot
ExecStart=/opt/FurryReadingBot/.venv/bin/python bot.py
Restart=always
RestartSec=5
Environment=PYTHONUNBUFFERED=1

[Install]
WantedBy=multi-user.target
```

```bash
sudo systemctl daemon-reload
sudo systemctl enable --now furryreadingbot
journalctl -u furryreadingbot -f
```

### 8.2 数据同步定时器

定时把 `data/` 提交到私有仓库。它和 `/sync` 共用 `script/sync_data.sh`，脚本内部用 `flock` 串行，所以两边不会同时 `git commit / pull --rebase / push`。

| 文件 | 作用 |
|---|---|
| `deploy/furryreadingbot-sync.service` | `Type=oneshot`，执行 `/bin/bash .../script/sync_data.sh`；`TimeoutStartSec=180` 大于脚本里 60 秒的等锁上限，并给 git 留出执行时间 |
| `deploy/furryreadingbot-sync.timer` | `OnCalendar=hourly` + `Persistent=true`（停机期间错过的会补跑） |

```bash
sudo cp deploy/furryreadingbot-sync.service deploy/furryreadingbot-sync.timer /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable furryreadingbot-sync.timer
sudo systemctl restart furryreadingbot-sync.timer
systemctl list-timers furryreadingbot-sync.timer
journalctl -u furryreadingbot-sync -n 50
```

手工跑一次（没有数据变动时只会「跳过 / 补推」，不会产生空提交）：

```bash
sudo systemctl start furryreadingbot-sync.service
```

> 如果之前用 crontab 跑 `data/sync_data.sh`，先删掉旧行，避免和新 timer 重复触发；路径迁移见上文「从旧部署迁移」。

### 8.3 运维清单

| 频率 | 做什么 |
|---|---|
| 每天 | 看日志里的 `更新处理出错` / `Forbidden` / `异步请求 JSON 失败` |
| 每周 | 备份 `data/*.json` |
| 改名单后 | 名单 mtime 热加载，**不用重启**，下一条消息即生效 |
| 换 Token / 换频道 | 改 `.env` 后重启进程 |
| 撤销管理员 | 按频道权限判定，缓存 60 秒内生效 |

> 手工拉黑（直接改 `black_authors.json`）**不会**删除频道里的历史分享；只有作者下架申请核验通过（`rby`）才会自动删。清理历史分享前先看 [02 §4.3](02-用户使用流程.md)。

## 9. 常见启动 / 运行问题

| 现象 | 原因 | 处理 |
|---|---|---|
| `配置有误，请检查 .env` | 必需变量为空（`prod` 要 `FURRY_NOVELS` / `FURRY_READING`） | 按列出的问题补全 `.env`；`SHARE_MODE` 是 `config.py` 常量，写在 `.env` 里不生效 |
| 启动报 `ModuleNotFoundError: telegram` | 用了系统 Python 而不是 `.venv` | 用 `.venv\Scripts\python.exe bot.py` |
| 申请提示没能送到管理员 | Bot 不是中转频道管理员，或频道 ID 填错 | 检查 `TRANSIT_CHANNEL` 与 Bot 权限 |
| 分享提示「没有可用的分享频道」 | 当前模式对应的频道变量为空 | `test` 看 `TEST_CHANNEL`，`prod` 看 `FURRY_NOVELS` |
| 下载失败、日志 `异步请求 JSON 失败` | 服务器连不上 `linpx.ink`，或链接不是 Linpx | 换网络 / 加直连；确认链接域名 |
| 测试里 3 条 skip | 真实 API 用例默认关闭 | 需要时设 `LINPX_LIVE=1` |
| `test_style.py` 失败 | 某处用了空格缩进 | 按报错的文件:行号改成 Tab |
