## 0. 一句话

Python 3.12 + `uv sync` + `.env` + `data/*.json`，一条命令前台跑起来：**没有 Web 服务、没有任务队列**，断电风险靠 JSON 原子写兜。README 只保留一句话入口，安装 / 配置 / 启动 / 测试 / 部署的完整步骤都在本文。

## 1. 环境要求

| 项 | 要求 | 说明 |
|---|---|---|
| Python | **3.12+** | `pyproject.toml` 的 `requires-python = ">=3.12"`；仓库带 `uv.lock` |
| 包管理 | 推荐 [uv](https://docs.astral.sh/uv/) | 没有 uv 也能用 `venv + pip`，见 §2 |
| 网络 | 能直连 `api.telegram.org`、`linpx.ink` 与 `pixiv.net` | 抓 Linpx / Pixiv 用 aiohttp，**不读 `HTTP(S)_PROXY`**；只有 Telegram 侧（httpx）会读代理变量。部署前先 `curl https://linpx.ink/`、`curl https://www.pixiv.net/` 确认直连可用 |
| Bot 身份 | 一个 Bot Token | 从 [@BotFather](https://t.me/BotFather) 申请 |
| 频道 | 分享 / 审核各需要频道，且 **Bot 必须是频道管理员** | 权限不足时表现为「发不出去」，日志里有 Telegram 报错 |
| 磁盘 | `data/`（KB~MB 级 JSON）+ `files/work/`（临时文件） | 交付后删除；启动时清空，进程被强杀留下的 `dl-*` 目录随下次启动回收 |

## 2. 安装

### 2.1 用 uv（推荐）

```powershell
git clone https://github.com/<owner>/FurryReadingBot.git
cd FurryReadingBot
uv sync
Copy-Item .env.example .env
```

```bash
git clone https://github.com/<owner>/FurryReadingBot.git
cd FurryReadingBot
uv sync
cp .env.example .env
```

`<owner>` 换成实际仓库地址。`uv sync` 会按 `uv.lock` 建好 `.venv/`，后面所有命令都跑 `.venv` 里的解释器；`.env` 至少填 `BOT_TOKEN` 与 `TEST_CHANNEL`（见 §4.1）。

### 2.2 不用 uv

仓库**没有** `requirements.txt`，依赖清单以 `pyproject.toml` 为准：

```powershell
python -m venv .venv
.venv\Scripts\python.exe -m pip install -U pip
.venv\Scripts\python.exe -m pip install "python-telegram-bot>=22.8" "aiohttp>=3.14.5" "aiofiles>=25.1.0" "pyzipper>=0.4.0" "requests>=2.34.2" "python-dotenv>=1.2.4"
```

> `pytest` 在 `pyproject.toml` 的 `[dependency-groups].dev` 里（运行时不需要）；要跑测试再单独 `.venv\Scripts\python.exe -m pip install pytest`。

## 3. 数据目录

| 路径 | 是什么 | 要不要提交 |
|---|---|---|
| `data/*.json` | 运行时状态：名单、兽人作者申请、作者下架申请、`file_id` 缓存、请求缓存（`fetch_cache.json`，`get_json` 按 URL 缓存的响应）、分享记录、未识别标签（`unknown_tags.json`，首次遇到未识别写法时自动建） | **不要**。根仓库 `.gitignore` 里有 `data/*.json` |
| `data/tags.toml` | 标签词表（词表源文件，见 [08](08-标签词表.md)） | **不要**。改完在数据目录提交；`/sync` 只提交 `*.json`，不会带上它 |
| `data.example/` | 模板：6 份 JSON + `tags.toml`（标签词表样例）。`furry_authors.json` 含一份公开的**兽人作者名单**；其余 JSON 是空结构（`black_request.json` 模板里没有，首次运行会自动建） | 可以，它是模板 |
| `files/work/` | 下载打包目录，交付后删除 | **不要**，已 gitignore |

> `sync_data.sh` / `sync_data.ps1` **不在 `data/` 里**：它们和 Bot 代码一起放在 `script/`（根仓库跟踪）。`data/` 保持纯数据，换机器时把数据目录一起带走即可；脚本只有一份，不会出现两个版本对不上的问题。

首次运行时的行为：

- 任何缺失的 JSON 会被 `JsonStore` **自动创建**为空结构（`storage/json_store.py`），所以 `test` 模式下只填 `BOT_TOKEN` + `TEST_CHANNEL` 也能启动，只是所有作者都不在名单里 → 全部走「申请」。
- 想让 Bot 开箱可用，把模板拷进 `data/`（JSON + `tags.toml`，别带 `data.example/.idea/` 那份历史残留）：

```powershell
New-Item -ItemType Directory -Force -Path data | Out-Null
Copy-Item data.example\*.json,data.example\tags.toml data\
```

```bash
mkdir -p data && cp data.example/*.json data.example/tags.toml data/
```

`data/` 目录只放运行数据；名单的备份 / 同步在 `data/` 单独操作。Bot 的 `/sync` 在 Linux 上执行 `script/sync_data.sh`、在 Windows 上执行内容等价的 `script/sync_data.ps1`；两个脚本按自身位置找 `../data`，所以定时任务里也要写 `script/` 下的路径。

## 4. 配置项（`.env` + `config.py` 常量）

`.env` 只放**部署相关**的 Token、频道 ID 与 Pixiv 登录态；评分阈值、update 并发数，以及所有 TTL / 冷却 / 有效期（请求缓存、`file_id`、分享冷却、分享记录保留、下架申请时限）都是 `config.py` 里的**代码常量**，跟着代码同步，不需要在仓库里再配密钥。

> 用 GitHub Actions 自动部署时，`.env` 由仓库 Secrets **每次覆盖生成**（规则见 §8.2）；手工部署才需要自己维护 `.env`。

从 `.env.example` 复制后填。`config.py` 用 `python-dotenv` + `os.environ` 读取，启动时由 `config_errors()` 检查必需项，缺失直接 `SystemExit` 并列出问题。

| 变量 | 必填 | 默认 | 作用 |
|---|---|---|---|
| `BOT_TOKEN` | ✅ | — | Bot Token。**缺失时进程直接 `SystemExit`** |
| `TEST_CHANNEL` | `test` 必填 | 空 | `SHARE_MODE=test` 时唯一的分享目标；也是 `TRANSIT_CHANNEL` 的回退值 |
| `TRANSIT_CHANNEL` | 可选 | `TEST_CHANNEL` | 中转频道：待审申请（兽人作者申请、作者下架申请）+ 标签未确认兽人小说的分享；未配置时一律复用 `TEST_CHANNEL` |
| `FURRY_READING` | `prod` 必填 | 空 | 兽人阅读频道；`prod` 下评分达标时同时发这里；也是分享文案里的「支持频道」 |
| `FURRY_NOVELS` | `prod` 必填 | 空 | 兽人小说频道；`prod` 下所有分享都发这里 |
| `FURRY_READING_NEW_GROUP` / `TEST_GROUP` | 可选 | 空 | 分享时**同时发到群组**（文件 / caption / 键盘与频道一致）：`prod` 用 `FURRY_READING_NEW_GROUP`，`test` 用 `TEST_GROUP`；未配置则跳过。群消息也写入分享记录，下架时一并删除 |
| `PIXIV_COOKIE` | ✅ | — | Pixiv 原站登录态；**启动必填**（`config_errors()` 缺失直接退出：P 站小说不能只取公开内容）。推荐只填 `PHPSESSID` 的值（也兼容完整 Cookie 串）；支持用双引号包裹后**换行**或用 **`||`** 分隔多个账号轮换（随机起始、单号连续 100 次切下一号、单号间隔 0.5s + 同 IP 全局间隔 0.3s + 0~0.2s 随机抖动、401/403 故障转移、429 单号冷却 15 分钟自动恢复）。登录态失效时 R18 正文 / 系列会明确提示需要配置，而不是给出空文件 |

**行为参数（`config.py` 常量，不在 `.env`）**

这些不是密钥，也不通过环境变量读取；改 `config.py` 后提交、重新部署即生效。

| 常量（数值见 `config.py`） | 作用 |
|---|---|
| `SHARE_MODE` | `test` 只发 `TEST_CHANNEL`；`prod` 按评分分流到正式频道。只能是 `test` / `prod`，其他值启动失败 |
| `SHARE_SCORE_THRESHOLD` | `prod` 下同时发 `FURRY_READING` 的评分下限（评分在下载时算好、随 `file_id` 写进缓存） |
| `CONCURRENT_UPDATES` | update 并发数；必须是正整数（`0` / 负数会让 PTB 在建 `Application` 时抛 `ValueError`），`1` = 串行 |

时间参数（`config.py` 里按「一次使用流程」的先后顺序排列，`storage/` 里不再各留一份默认值）：

| 常量（数值见 `config.py`） | 作用 |
|---|---|
| `FETCH_CACHE_TTL_HOURS` | ① 抓来源：请求缓存有效期（小时）。同一链接（URL）的 JSON 响应直接复用，预检 / 解析系列 / 打包不再重复请求；写进 `data/fetch_cache.json` |
| `FILE_CACHE_TTL_DAYS` | ② 下载产物：`file_id` 缓存有效期（天）；命中就直接复用，不再上传 |
| `SHARE_COOLDOWN_DAYS` | ③ 分享：同一作品重复分享的冷却天数 |
| `SHARE_RECORD_TTL_DAYS` | ④ 分享记录：频道消息保留天数；下架核验通过后按记录回溯删除 |
| `BLACK_REQUEST_MATERIAL_TTL_MINUTES` | ⑤ 下架申请：点「申请下架」后提交后台截图的时限（分钟），过期作废 |
| `APPLY_COOLDOWN_HOURS` | ⑥ 申请冷却：同一作者在该时间（小时）内只能申请一次（兽人名单 / 黑名单共用；兽人名单按提交申请算，黑名单按提交截图送审算） |
| `FURRY_REQUEST_TTL_DAYS` | ⑦ 申请记录保留：已结束（通过 / 拒绝）的兽人作者申请保留天数；`pending` 记录不按 TTL 淘汰 |
| `BLACK_REQUEST_TTL_DAYS` | ⑦ 申请记录保留：已结束（通过 / 拒绝）的下架申请保留天数（拉黑凭据，默认比兽人申请长）；`pending_material` / `pending_review` 不按 TTL 淘汰 |

关于默认值的三个坑：

1. 所有 TTL / 冷却 / 有效期只在 `config.py` 定义（`FETCH_CACHE_TTL_HOURS` / `FILE_CACHE_TTL_DAYS` / `SHARE_COOLDOWN_DAYS` / `SHARE_RECORD_TTL_DAYS` / `BLACK_REQUEST_MATERIAL_TTL_MINUTES` / `APPLY_COOLDOWN_HOURS` / `FURRY_REQUEST_TTL_DAYS` / `BLACK_REQUEST_TTL_DAYS`）：`storage/` 的 Store 构造时不传就现读 config，测试可显式传值覆盖。
2. `TRANSIT_CHANNEL` 未配置时**任何模式**都会回落到 `TEST_CHANNEL`；`config_errors()` 里 `prod` 仍把它列为必填，但因为有回退，只有 `TEST_CHANNEL` 也为空时才会报错。
3. 启动校验只检查「有没有填」：填错的频道 ID 不会立刻报错，直到真正发消息才失败。

频道既可以填数字 ID（`-1001234567890`），也可以填公开频道的 `@username` —— 都是原样交给 Telegram API。

### 4.1 最小可运行

`SHARE_MODE` 是代码常量（当前 `prod`），最小配置要覆盖 `prod` 的频道 + 启动必填的 `PIXIV_COOKIE`（`TRANSIT_CHANNEL` 未配会回退 `TEST_CHANNEL`，两者都空同样启动失败）：

```dotenv
BOT_TOKEN=123456:AA...
PIXIV_COOKIE="111111111_xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx"
FURRY_NOVELS=@furry_novels
FURRY_READING=-1001234567891
TRANSIT_CHANNEL=-1001234567892
```

只填 `BOT_TOKEN` + 频道会启动失败（`config_errors()` 会列出缺 `PIXIV_COOKIE` 等项）。想在本地只往测试频道发，先把 `config.py` 的 `SHARE_MODE` 改成 `"test"` 再这样配：

```dotenv
BOT_TOKEN=123456:AA...
PIXIV_COOKIE="111111111_xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx"
TEST_CHANNEL=-1001234567890
```

此时分享只发 `TEST_CHANNEL`，审核也用 `TEST_CHANNEL`。

### 4.2 生产形态

```dotenv
BOT_TOKEN=123456:AA...
FURRY_NOVELS=@furry_novels
FURRY_READING=-1001234567891
TRANSIT_CHANNEL=-1001234567892
# PIXIV_COOKIE 是启动必填（R18 必需）；多账号可换行或 || 分隔：
PIXIV_COOKIE="111111111_xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx
222222222_yyyyyyyyyyyyyyyyyyyyyyyyyyyyyyyy"
```

> `prod` 下作品下载时按 `read_count` / `like_count` 算推荐指数并写进 `files_cache.json`；分享时 `score >= SHARE_SCORE_THRESHOLD` 会同时发 `FURRY_READING`，否则只发 `FURRY_NOVELS`。txt 分享一定有评分（作者整包没有统计，按低分处理）。规则见 [01 §1](01-功能清单与缺口.md) 与 `policy/scoring.py`。

## 5. 启动

```powershell
.venv\Scripts\python.exe bot.py
```

```bash
.venv/bin/python bot.py
```

- 日志走 stdout（`logging.basicConfig`，INFO 级）；`Bot 启动中……` 之后进入 **long polling**。
- `drop_pending_updates=False`：停机期间的消息会在重启后补处理。
- 并发：`Application.builder().concurrent_updates(CONCURRENT_UPDATES)` 并行处理 update；数值是 `config.py` 常量（`CONCURRENT_UPDATES`，`1` = 串行），改代码后重新部署生效。不要用 `True`（PTB 里等于 256 路）。
- `post_shutdown` 通过 builder 注册（v20+ 里它不是 setter），退出时关掉复用的 aiohttp 会话。
- 同一链接的下载由 `DownloadService` 内的 `asyncio.Lock` 串行：第二次请求会等第一次传完并直接复用 `file_id`，不会重复抓取 / 上传；每次打包都在独立工作目录，不同作品仍并行。
- `/sync` 分两步：① `services/import_author_service.py` 先调 `sources/linpx/client.get_fav_users()` 抓 `https://api.linpx.ink/fav/user/cache`，把作者并入 `data/furry_authors.json`（note = `Linpx`；已收录 / 黑名单作者跳过）；② `services/sync_service.py` 执行同步脚本（超时 300 秒）把结果提交。Linux 用 `/bin/bash script/sync_data.sh`，Windows 用 `powershell.exe -NoProfile -ExecutionPolicy Bypass -File script/sync_data.ps1`。两个脚本**契约一致**（退出码 0/2/3/4/5、锁文件、跳过与提交文案），实现按平台各自最优（`.sh` 用 `flock -w 60`，`.ps1` 用「独占打开文件」）；**定时任务与 `/sync` 会排队执行**，不会同时 `git commit / pull --rebase / push`；Bot 侧再加一把进程内锁，连点 `/sync` 也不会拉起多个脚本。
- 推荐作者抓取走 `infra.http.get_json`：单次 30 秒超时、最多 3 次重试（1s / 2s 退避），最坏约 90 秒；这段不计入脚本的 300 秒预算，期间 Telegram 侧只看到「⏳」。
- 提交范围：脚本只 `git add -- ':(glob)*.json'`，即 `data/*.json`（**不递归子目录**）；`data/eval/`、`README.md` 等不会被 `/sync` 顺带提交，没有 JSON 变动就直接跳过。
- 提交身份：脚本用 `git -c user.name=… -c user.email=…` 只给本次提交用 bot 身份，**不会写进 `data/.git/config`**；你之后在 `data/` 里手动 `git commit` 仍是自己的身份。若仓库里残留过旧脚本写死的 bot 身份，手动清一次：`git -C data config --local --unset-all user.name`、`git -C data config --local --unset-all user.email`。
- 服务器定时任务只调 `script/sync_data.sh`，不经过 Bot、不联网抓推荐作者；推荐作者只在手动 `/sync` 时合并。抓取失败（接口 5xx / 超时）不会阻止提交，回复里会单独提示「Linpx 推荐作者抓取失败」；接口 404 或返回空列表按「0 个推荐作者」处理。
- **从旧部署迁移**：脚本已从 `data/` 移到 `script/`，crontab / 计划任务里的路径要同步改（`.../FurryReadingBot/data/sync_data.sh` → `.../FurryReadingBot/script/sync_data.sh`）；旧路径会直接找不到文件。仓库现在自带 systemd timer（见 §8.3），可以删掉旧的 crontab 行。数据仓库不再需要保留这两份脚本，删掉即可。
- 超时处理：先 `taskkill /F /T` 杀掉整棵进程树（Windows 上只杀 powershell 会留下握着仓库锁的 `git`），再最多等 5 秒回收已产生的输出。**不要**在超时后再调 `communicate()`——Windows 上被取消过的那次调用会永远等不到 EOF，`/sync` 会一直卡在锁上。
- Windows 上跑 `/sync` 的前提：系统自带的 `powershell.exe` + 已对私有数据仓库配好 git 凭据。脚本会设置 `GIT_TERMINAL_PROMPT=0` / `GCM_INTERACTIVE=never`，凭据缺失时直接失败并回显，不会停下来等输入。
- `/sync` 与 `/review` 共用一套权限：仅中转频道 `creator` / `administrator` 可用（`AdminPolicy`，默认拒绝；成员状态缓存 60 秒，撤权最多延迟一分钟）。非管理员只会收到「⚠️ 仅中转频道管理员可以同步运营数据」，不会触发脚本。`TRANSIT_CHANNEL` 与 `TEST_CHANNEL` 都未配置时没人能通过校验。
- 不启动轮询、只验证装配：

```powershell
.venv\Scripts\python.exe -c "import bot; print('import ok')"
```

### 5.1 上线自检清单

| # | 检查 | 不满足时的现象 |
|---|---|---|
| 1 | `.env` 里 `BOT_TOKEN` 有效 | 无效 Token 在 `run_polling` 阶段抛 `Unauthorized` |
| 2 | Bot 已加入所有频道 / 群组并设为管理员 | 分享 / 中转消息发不出去，日志里 `Forbidden` / `chat not found`；群组失败时用户回执会补「群组发送失败」 |
| 3 | 中转频道建议设为**私有** | 管理员判定看该频道的成员身份，私有能少一堆误触 |
| 4 | `data/furry_authors.json` 非空 | 空名单 → 所有作者都要走申请 |
| 5 | `files/work/` 可写、磁盘有余量 | 抓取 / 保存失败 |
| 6 | 服务器能直连 `linpx.ink` 与 `www.pixiv.net`；`PIXIV_COOKIE` 已配置（启动必填，缺失进程直接退出） | 启动失败列出「PIXIV_COOKIE 未配置」，或下载提示抓取失败 / 「需要配置 PIXIV_COOKIE」 |
| 7 | 走自动部署时，`deploy` 分支的 Actions run 是绿的（§8.2） | `git reset` 成功但中途失败 → 代码更新了、服务没重启，线上仍是旧代码 |

## 8. 部署

### 8.1 现状

- 单进程、long polling、前台运行；重启只会丢内存里的 `_inflight`（分享并发保护）和下载串行锁，业务数据都在 JSON 里。
- 仓库 `deploy/` 里有三份 unit：bot 的 `furryreadingbot.service`、数据同步的 `furryreadingbot-sync.service` + `furryreadingbot-sync.timer`；**没有** Dockerfile、健康检查 / 指标（见 [01 §2 P2](01-功能清单与缺口.md)）。
- 线上形态是「一台机器 + systemd + GitHub Actions」：推送 `deploy` 分支后由 Actions SSH 到服务器更新代码、依赖、`.env` 与 unit，再重启服务（规则见 §8.2）。下面就是 `deploy/furryreadingbot.service` 的实际内容，`/root/FurryReadingBot` 与自动部署脚本里写死的路径一致：

```ini
[Unit]
Description=FurryReadingBot
After=network.target

[Service]
Type=simple
User=root
WorkingDirectory=/root/FurryReadingBot
ExecStart=/root/FurryReadingBot/.venv/bin/python bot.py
Restart=always
RestartSec=5
# 不缓冲 stdout：否则 journalctl 里的日志会成块延迟出现
Environment=PYTHONUNBUFFERED=1
StandardOutput=journal
StandardError=journal

[Install]
WantedBy=multi-user.target
```

> 换目录 / 换用户要**三处一起改**：`deploy/*.service` 的 `WorkingDirectory` / `ExecStart`、`.github/workflows/deploy.yml` 里写死的 `/root/FurryReadingBot` 与 `/etc/systemd/system`、以及 `SSH_USER` 的权限。纯手工部署时 unit 里的 `User=` 可以删掉，路径放到 `/opt` 下也行。

```bash
sudo systemctl daemon-reload
sudo systemctl enable --now furryreadingbot
journalctl -u furryreadingbot -f
```

### 8.2 GitHub Actions 自动部署（`deploy` 分支）

推送 `deploy` 分支（或手动 `workflow_dispatch`）触发 `.github/workflows/deploy.yml`：runner 上用 `appleboy/ssh-action@v1.2.0`（内置 drone-ssh 1.8.0）SSH 登录服务器，把整段脚本作为**一条命令**执行。`concurrency: deploy-production` + `cancel-in-progress: false`：连推两次会排队，不会有两个 runner 同时 `git reset` / `systemctl restart`。

| 步骤 | 做什么 | 关键点 |
|---|---|---|
| 1 | 主代码仓库 | 首次 `git clone -b deploy`；之后 `git fetch origin deploy` + `git reset --hard origin/deploy`。**服务器上对代码的手改会被丢弃**；`data/` 是 gitignore 的未跟踪目录，不受影响 |
| 2 | 数据仓库（私有） | `data/.git` 不存在 → `rm -rf data` + `git clone <PRIVATE_REPO>`（重建整个目录）；存在 → `git fetch origin main` + `git stash` + `git merge origin/main --ff-only` + `git stash pop`，冲突时 `merge --abort` 并**以服务器本地为准** |
| 3 | Python 环境 | 没有 `uv` 就装到 `~/.local/bin`，`export PATH="$HOME/.local/bin:$PATH"`，`uv sync` 按 `uv.lock` 同步 `.venv` |
| 4 | 生成 `.env` | 用 Secrets 覆盖写入（§8.2.2），再校验 4 个键非空 |
| 5 | systemd | `cp deploy/*.service` 与 `deploy/*.timer` 到 `/etc/systemd/system/` → `daemon-reload` → `enable` + `restart furryreadingbot` → `enable` + `restart furryreadingbot-sync.timer`（需要 root） |
| 6 | 启动校验 | `sleep 5` 后 `systemctl is-active --quiet furryreadingbot`，失败就打印 `journalctl -n 50` 并 `exit 1` |

脚本首行是 `set -Eeuo pipefail`，紧跟一行 `trap 'echo "部署失败：第 $LINENO 行，退出码 $?"' ERR`：任一命令非 0 立刻中断，日志里带行号。`if` 条件、`cmd || true`、`cmd || { …; }` 里的失败不会中断。整段脚本受 `command_timeout` 限制（默认 **10 分钟**，`uv sync` 慢就调大）。

#### 8.2.1 Secrets 清单

在仓库 `Settings → Secrets and variables → Actions` 里配，**不是仓库内的文件**；runner 上先把 `${{ secrets.X }}` 替换成明文，再经 SSH 发到服务器执行。

| Secret | 用途 | 必需 | 写进 `.env` |
|---|---|---|---|
| `SSH_HOST` / `SSH_USER` / `SSH_PORT` | 登录地址、用户、端口（**建议显式填 `22`**；留空时 action 的默认值会被空字符串覆盖，drone-ssh 解析端口会失败） | ✅ | 否 |
| `SSH_PRIVATE_KEY` | 登录私钥 | ✅ | 否 |
| `PRIVATE_REPO` | 私有数据仓库 `owner/repo` | 步骤 2 需要 | 否 |
| `PRIVATE_REPO_TOKEN` | 读写私有仓库的 PAT（拼进 clone URL） | 步骤 2 需要 | 否 |
| `BOT_TOKEN` | Bot Token | ✅（被校验） | ✅ |
| `FURRY_READING` / `FURRY_NOVELS` | 正式频道（`SHARE_MODE=prod`） | ✅（被校验） | ✅ |
| `TEST_CHANNEL` | 测试频道，也是 `TRANSIT_CHANNEL` 的回退值 | ✅（被校验） | ✅ |
| `TRANSIT_CHANNEL` | 中转频道（审核、待确认分享） | 可选 | ✅ |
| `FURRY_READING_NEW_GROUP` / `TEST_GROUP` | 分享时同时发群组（`prod` / `test` 各一个；不配则跳过） | 可选 | ✅ |
| `PIXIV_COOKIE` | Pixiv 登录态（推荐裸 `PHPSESSID`，也兼容完整 Cookie 串；多账号可换行或 `||` 分隔） | 必填（启动校验） | ✅ |

> `.env` 里只有这 8 个键；`SHARE_MODE`、`SHARE_SCORE_THRESHOLD`、`CONCURRENT_UPDATES` 以及所有 TTL / 冷却 / 有效期（`FETCH_CACHE_TTL_HOURS`、`FILE_CACHE_TTL_DAYS`、`SHARE_COOLDOWN_DAYS`、`SHARE_RECORD_TTL_DAYS`、`BLACK_REQUEST_MATERIAL_TTL_MINUTES`、`APPLY_COOLDOWN_HOURS`）都是 `config.py` 常量（§4），配成 Secret 也不会生效。

#### 8.2.2 `.env` 生成规则

```bash
cat > .env <<'EOF'
BOT_TOKEN="${{ secrets.BOT_TOKEN }}"
# …其余频道 ID 同理…
PIXIV_COOKIE="${{ secrets.PIXIV_COOKIE }}"
EOF
```

- **每次部署全量覆盖**：`cat >` 不是追加，**在服务器上手改 `.env` 下次部署就没了**；要长期生效只能改 Secret（或改用 §8.1 的手工部署）。
- **没配 Secret = 空字符串**：写成 `KEY=""`，不会报「未定义」。`BOT_TOKEN` / `PIXIV_COOKIE` / `FURRY_READING` / `FURRY_NOVELS` / `TEST_CHANNEL` 会被 `grep -qE '^KEY="..*"'` 拦下并 `exit 1`；`TRANSIT_CHANNEL` / `*_GROUP` 留空是合法的「未配置」。
- 校验的 5 个键和 `config_errors()` 不完全等同：`prod` 需要的 `TRANSIT_CHANNEL` 空时会回退 `TEST_CHANNEL`，所以校验 `TEST_CHANNEL` 已经覆盖；但**填错的频道 ID 拦不住**，要等真正发消息才报错（§4 坑 3）。
- heredoc 用带引号的 `<<'EOF'`，Secret 里的 `$` / 反引号不会被 shell 二次展开；但值里若有 `"` 会破坏 `.env` 的双引号（`PHPSESSID` 一般是字母数字，安全）。
- **不要开 `debug: true`**：drone-ssh 的 debug 会把整段脚本（含明文 Secret）打进 Actions 日志。正常模式下 GitHub 会把已知 Secret 值掩码成 `***`。

#### 8.2.3 已知坑与排查

| 现象 | 原因 | 处理 |
|---|---|---|
| `Process exited with status 1`，日志停在 `HEAD is now at …`，之后没有任何 echo | 开了 `script_stop: true`：drone-ssh 会把脚本按行拆开、每行后插一条 `if [ $? -ne 0 ]` 检查；`if/else` 的 `else` 分支一进去 `$?` 还是 if 条件的 1 → 静默 `exit 1`。heredoc 内容也会被这些检查行写脏 | **不要开 `script_stop`**，用首行的 `set -e` 实现「失败即中断」（2026-11-25 起已去掉） |
| `部署失败：第 N 行，退出码 X` | `ERR` trap 打的行号 | 按 `deploy.yml` 第 N 行定位：数据仓库 `fetch`、权限、频道 Secret 为空是常见原因 |
| `Error: command timeout` | 整段脚本超过 `command_timeout`（默认 10 分钟） | 给 step 加 `command_timeout: 20m` |
| `fatal: couldn't find remote ref main` | 私有数据仓库默认分支不是 `main`（脚本写死 `origin main`） | 统一私有仓库分支名，或改 `deploy.yml` |
| `cp: cannot create regular file '/etc/systemd/system/…': Permission denied` / `systemctl: command not found` | `SSH_USER` 不是 root 也没有免密 sudo | 用 root，或在脚本里加 `sudo` |
| `错误：.env 里的 X 为空，请检查仓库 Secrets。` | 对应 Secret 没配或被删 | 补 Secret 后重跑 |
| 进程活着但行为不对（频道 ID 错、R18 不可用） | 步骤 6 只检查「进程没退」 | 看 `journalctl -u furryreadingbot -n 50`；确认 `PIXIV_COOKIE` 已配 |

> workflow 改完必须提交到 **`deploy` 分支**才生效（Actions 执行的是被推送分支里的这份文件）；`main` 同步提交只是让两个分支内容一致。

### 8.3 数据同步定时器

定时把 `data/` 提交到私有仓库。它和 `/sync` 共用 `script/sync_data.sh`，脚本内部用 `flock` 串行，所以两边不会同时 `git commit / pull --rebase / push`。

> 走 §8.2 的自动部署时，这三份 unit 每次都会被 `cp` 到 `/etc/systemd/system/` 并重启 timer，**不需要手工复制**；只有纯手工部署才执行下面的命令。

| 文件 | 作用 |
|---|---|
| `deploy/furryreadingbot-sync.service` | `Type=oneshot`，执行 `/bin/bash .../script/sync_data.sh`；`TimeoutStartSec=180` 大于脚本里 60 秒的等锁上限，并给 git 留出执行时间 |
| `deploy/furryreadingbot-sync.timer` | `OnCalendar=hourly` + `Persistent=true`（停机期间错过的会补跑） |

```bash
sudo cp deploy/furryreadingbot-sync.service deploy/furryreadingbot-sync.timer /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable furryreadingbot-sync.timer
sudo systemctl restart furryreadingbot-sync.timer
systemctl list-timers furryreadingbot-sync.timer
journalctl -u furryreadingbot-sync -n 50
```

手工跑一次（没有数据变动时只会「跳过 / 补推」，不会产生空提交）：

```bash
sudo systemctl start furryreadingbot-sync.service
```

> 如果之前用 crontab 跑 `data/sync_data.sh`，先删掉旧行，避免和新 timer 重复触发；路径迁移见上文「从旧部署迁移」。

### 8.4 运维清单

| 频率 | 做什么 |
|---|---|
| 每天 | 看日志里的 `更新处理出错` / `Forbidden` / `异步请求 JSON 失败` |
| 每周 | 备份 `data/*.json` |
| 改名单后 | 名单 mtime 热加载，**不用重启**，下一条消息即生效 |
| 换 Token / 换频道 | 自动部署：改对应 Secret 后重跑 workflow（`.env` 每次都会被重写）；手工部署：改 `.env` 后重启进程 |
| 改部署目录 / 用户 | 三处一起改：`deploy/*.service`、`deploy.yml` 里的固定路径、`SSH_USER` 权限（见 §8.1） |
| 撤销管理员 | 按频道权限判定，缓存 60 秒内生效 |

> 手工拉黑（直接改 `black_authors.json`）**不会**删除频道里的历史分享；只有作者下架申请核验通过（`rby`）才会自动删。清理历史分享前先看 [02 §4.3](02-用户使用流程.md)。

## 9. 常见启动 / 运行问题

| 现象 | 原因 | 处理 |
|---|---|---|
| `配置有误，请检查 .env` | 必需变量为空（`prod` 要 `FURRY_NOVELS` / `FURRY_READING`） | 按列出的问题补全 `.env`；`SHARE_MODE` 是 `config.py` 常量，写在 `.env` 里不生效 |
| 启动报 `ModuleNotFoundError: telegram` | 用了系统 Python 而不是 `.venv` | 用 `.venv\Scripts\python.exe bot.py` |
| 申请提示没能送到管理员 | Bot 不是中转频道管理员，或频道 ID 填错 | 检查 `TRANSIT_CHANNEL` 与 Bot 权限 |
| 分享提示「未配置分享频道」/「未配置中转频道」 | 当前模式对应的频道变量为空 | 正式频道：`test` 看 `TEST_CHANNEL`，`prod` 看 `FURRY_NOVELS`；中转：看 `TRANSIT_CHANNEL` |
| 下载失败、日志 `异步请求 JSON 失败` | 服务器连不上 `linpx.ink`，或链接不是 Linpx | 换网络 / 加直连；确认链接域名 |
| 测试里 5 条 skip | 真实 API 用例默认关闭（3 条 Linpx + 2 条 Pixiv） | 需要时设 `LINPX_LIVE=1` / `PIXIV_LIVE=1` |
| `test_style.py` 失败 | 某处用了空格缩进 | 按报错的文件:行号改成 Tab |
| Actions 报 `Process exited with status 1`，日志停在 `HEAD is now at …` | 开了 `script_stop`（drone-ssh 行级注入让 `else` 分支静默退出），或某条命令失败 | 见 §8.2.3：先找 `部署失败：第 N 行，退出码 X`，再按行号定位；确认 `script_stop` 没开 |
| 手改服务器 `.env` 后重启，下次部署又变回去 | 自动部署每次用 Secrets 覆盖生成 `.env` | 改对应 Secret 后重跑 workflow（§8.2.2），或改用手工部署 |
