## 0. 一句话概括

用户在私聊里发送 **Linpx 小说 / 系列 / 作者链接**，Bot 先按作者维度做黑白名单与兽人作者名单校验，通过后生成 `txt` / `zip` 文件回传；用户可以把 `txt` 一键分享到指定频道；未收录的作者可以由用户发起申请，由管理员在**中转频道**人工核验后加入兽人作者名单。

当前 Bot 是「**按作者授权 + 人工审核**」模式，**没有**基于标签/正文的自动兽人内容识别，也**没有**翻译功能。

## 2. 已实现功能明细

### 2.1 入口与命令

- `bot.py` 使用 `Application.builder().token(...).build()` 构建应用，注册：
  - `CommandHandler("start", start)`
  - `CommandHandler("help", help_cmd)`
  - `CommandHandler("ping", ping)`
  - `CommandHandler("down", download)`
  - `CommandHandler("review", review)`
  - `MessageHandler(filters.TEXT & ~filters.COMMAND & filters.ChatType.PRIVATE, download)`
  - `CallbackQueryHandler(button_callback)`
- 未显式配置 `concurrent_updates`，PTB 默认按顺序处理更新；一个作者全量下载会阻塞其他用户。
- `error_handler` 只写日志，不向用户返回错误提示。
- `/start` 文案仍是「这是一个空壳 Bot」，与当前功能不符。

### 2.2 链接与来源解析

支持的 Linpx 链接（`sources/linpx/config.py`）：

| 类型 | 示例 |
|---|---|
| 单篇 | `https://linpx.ink/pixiv/novel/18012577` |
| 单篇短链 | `https://linpx.ink/pn/18012577` |
| 系列 | `https://linpx.ink/pixiv/series/16181401` |
| 系列 API | `https://api.linpx.ink/pixiv/series/16181401/cache` |
| 作者 | `https://linpx.ink/pixiv/user/130586197` |
| 作者短链 | `https://linpx.ink/pu/130586197` |

也兼容 `furrynovel.ink` / `furrynovel.xyz` 域名。

- `sources/__init__.py` 维护 `_SOURCES = [LinpxSource()]`，按 `can_handle` 选择来源。
- `fetch(link)` 根据链接类型返回 `Novel` / `Series` / `Author`。
- `resolve_link(link, "series")` 在单篇属于系列时，把目标解析成系列链接。
- `save(link, ext)` 根据类型和扩展名生成 txt / zip。
- **Pixiv 直链目前不支持**：`sources/pixiv/` 只有 URL 拼接函数，没有 client、parse 和 `NovelSource` 实现，也没有注册到 `_SOURCES`。

### 2.3 内容生成规则

- 单篇 txt：标题、作者、链接、标签、简介，随后是正文。
- 系列 txt：系列元信息 + 每章标题、简介、正文。
- 系列 zip：`save_series_zip` 按章保存为独立 txt，再压缩整个目录。
- 系列自动模式：
  - `is_real_series` 统计章节标题中的阿拉伯数字 / 中文数字出现次数；
  - 数字覆盖率 ≥ 75% 视为「真系列」→ 合并 txt；
  - 否则视为「合集 / 短篇集」→ 分章 zip。
- 作者全量：先下载作者所有系列，再下载不属于任何系列的单篇，最后压缩作者目录。
- 简介清洗：`<br>` 转行、去 `<strong>`、HTML 反转义、`pixiv://` 内链还原为 `pixiv.net` 链接。

### 2.4 权限判定（当前实际逻辑）

`handlers/download.py` 中的判定顺序：

1. 作者在 `black_authors.json` → 拒绝下载，提示改用 `@PixivNBot`。
2. 作者在 `furry_authors.json` → 显示作品信息 + 下载按钮。
3. 都不在 → 提示「本 Bot 仅可下载兽人小说」，并给出「✅ 申请」按钮。

补充说明：

- `white_authors.json`（授权转载白名单）**没有参与任何下载判定**，`is_whitelisted()` 只在测试里被调用。
- `ListManager.add_whitelist()` 会从黑名单移除，`add_blacklist()` 会从白名单移除，但不会同步处理 `furrylist`。
- 当前 `data/` 中：兽人作者约 460+ 位、黑名单 3 位、白名单 0 位；申请记录数量以 `apply_authors.json` 为准。
- `handlers/download.py` 只做元信息预检，真正的文件生成在 `handlers/callbacks/download.py`。

### 2.5 申请与审核

用户侧：

1. 点击「✅ 申请」→ `af`：先检查黑名单 / 已在兽人名单 / 已有待审记录。
2. 展示后果告知：通过后才能下载分享、审核期间不能下载、作者可投诉下架。
3. 点击「✅ 确认」→ `afy`：再次校验后写入 `data/apply_authors.json`，`count + 1`，状态重置为 `pending`。
4. 向 `TRANSIT_CHANNEL` 发送核验卡片：
   - `#兽人作者申请`
   - 作者名 / 作者 ID / 主页链接
   - 申请用户 / 申请次数
   - 「✅ 通过」「❌ 拒绝」「🏡 主页」按钮
5. 回复用户「已提交申请，管理员核验后会私聊通知结果」。

管理员侧：

- `afa`：状态改为 `approved`，写入兽人作者名单，删除中转卡片并留审核回执，私聊通知申请人。
- `afr`：状态改为 `rejected`，不加入任何名单，私聊通知申请人。
- `afb`：拒绝并加入黑名单。**代码存在但按钮被注释掉，当前无法从 UI 触发。**
- `/review`：把所有 `pending` 记录重新推送到中转频道。

已知问题：

- `/review` 和审核按钮**没有管理员身份校验**，能看见中转频道并能点击按钮的人都能审核。
- `review_application` 的「先读状态再改状态」没有使用 `set_status(expected=...)`，并发点击时存在竞态。
- `TRANSIT_CHANNEL` 为空时申请仍会写入成功，但 `send_to_transit` 只记 warning 并返回 `False`，管理员看不到申请。
- 审核通过后不会自动把作品发到正式频道，用户需要重新发送链接。

### 2.6 下载与缓存

按钮与动作：

| callback | 含义 | 产物 |
|---|---|---|
| `dn` | 下载本章 | 单篇 txt |
| `ds` | 系列自动 | 自动选 txt 或 zip |
| `dst` | 系列 txt | 合并 txt |
| `dsz` | 系列 zip | 分章 zip |
| `dan` | 作者全部下载 | 作者全量 zip |

缓存：

- key 形如 `novel:{id}:txt`、`series:{id}:zip`、`author:{id}:zip`。
- 由 `config.FILE_CACHE_TTL_DAYS` 控制，默认 7 天。
- 命中缓存直接复用 `file_id`，不再上传文件。
- 系列 `auto` 会依次尝试 `txt`、`zip` 缓存；两种都存在时让用户选择。
- 过期条目在读取或写盘时被清理。

上传：

- `upload_file` 支持 `path` 或 `file_id`，支持单目标 / 多目标。
- 本地文件上传成功后写入缓存；`cleanup=True` 时上传完删除本地文件。
- 文案超过 1024 字符会被截断（Telegram caption 限制）。

### 2.7 分享

- 只有 **txt** 会显示分享按钮；zip 返回空键盘（`share_novel_keyboard` 直接返回 `InlineKeyboardMarkup([[]])`）。
- `snp` 公开分享：文案带分享者名字。
- `sna` 私密分享：文案显示「匿名用户」。
- `snn` 拒绝分享：仅移除按钮。
- 分享前校验：
  - `_inflight` 集合防止并发重复分享；
  - `SHARE_COOLDOWN_DAYS`（默认 3 天）冷却；
  - 文件缓存必须仍然有效。
- 分享成功后写入 `data/share_records.json`（次数、最后分享者、频道、格式、公开/私密）。
- **当前目标频道写死为 `TEST_CHANNEL`**；`FURRY_READING`、`FURRY_NOVELS`、`FURRY_READING_NEW_GROUP` 的列表被注释掉，但用户提示仍写「已经公开分享至 {FURRY_READING}」。

### 2.9 下载业务层（本次重构）

下载相关流程已从 handler 收口到 `services/download_service.py`：

| 方法 | 职责 |
|---|---|
| `inspect_text` | 从消息提取唯一 URL，交给 `inspect_link` |
| `inspect_link` | 用 `resolve_source` + `is_*_link` 判断 novel / series / author，并拉取元信息 |
| `check_access` | 黑名单 / 兽人作者名单 / 需要申请 |
| `prepare` | 解析系列目标、查缓存、系列 auto 格式选择、fetch、save、推断扩展名 |
| `deliver` | 调用注入的 `upload` 适配器，并在 `finally` 中清理本地文件 |

边界：

- `services` 不 import telegram；
- `handlers/download.py` 只负责检查结果与键盘；
- `handlers/callbacks/download.py` 只负责 callback、消息编辑、上传适配；
- `handlers/telegram/upload.py` 仍是 Telegram 上传适配器，`get_cache()` 现在复用 `storage.file_cache.get_default_cache()`。

附带改进：

- 不支持的链接返回明确提示，不再抛 `AttributeError`；
- 上传失败也会清理本地临时文件；
- `file_id` 缓存改为进程级共享，下载与分享使用同一个 Store；
- 新增 `test/test_download_service.py`，17 个用例全部通过。

### 2.10 申请业务层（本次重构）

申请流程已从 `handlers/callbacks/apply.py` 收口到 `services/apply_service.py`：

| 方法 | 职责 |
|---|---|
| `inspect` | 解析作者 ID、黑名单 / 兽人名单校验、重复待审检查、拉取作者名 |
| `submit` | 再次检查 → 写入申请记录 → 调用注入的 `send_transit` → 返回提交结果 |
| `pending_records` | 返回全部 `pending` 申请，供 `/review` 重推 |
| `get_applications` | 进程级 `ApplicationStore` 单例，申请与审核共用 |

状态：

| status | 含义 |
|---|---|
| `needs_confirm` | 可以申请，返回 `af` 的二次确认 |
| `pending` | 已有待审记录，不重复写入 |
| `blacklisted` | 作者在黑名单，禁止申请 |
| `already_furry` | 作者已在兽人名单，无需申请 |
| `submitted` | 已写入记录并尝试送中转 |

边界：

- `services` 不 import telegram；
- `apply.py` 只负责 `apply_notice` 文案、`confirm_author_keyboard`、`edit_or_reply`；
- `handlers.telegram.send_to_transit` 仍是 Telegram 适配器，由 handler 以 lambda 注入；
- `/review` 改为 `ApplyService().pending_records()`，不再直接读 `ApplicationStore`；
- `get_applications()` 单例从 `handlers.callbacks.common` 移到 `services.apply_service`。

附带改进：

- 申请链接解析不出作者 ID 时返回明确提示；
- 提交前二次检查 pending，降低并发重复申请概率；
- 送中转失败只记日志，不影响申请记录已写入；
- 新增 `test/test_apply_service.py`，11 个用例全部通过。

### 2.11 审核业务层（本次重构）

审核流程已从 `handlers/callbacks/review.py` 收口到 `services/review_service.py`：

| 方法 | 职责 |
|---|---|
| `review(author_id, decision, reviewer...)` | 读取申请 → 检查 pending → 原子更新状态 → 更新名单 → 返回结果 |
| `decision` | `approve` / `reject` / `blacklist` |
| `ReviewResult.status` | `approved` / `rejected` / `missing` / `already_processed` |

关键实现：

- 使用 `ApplicationStore.set_status(..., expected=PENDING)` 保证同一申请只被成功处理一次；
- 审核通过：状态 `approved` + `add_furrylist`；
- 审核拒绝：状态 `rejected`；
- 拒绝并拉黑：状态 `rejected` + `add_blacklist`；
- 名单更新失败时，尝试把状态回滚到 `pending`，避免「状态已通过但名单没加」；
- 返回 `record`，handler 据此生成审核回执和申请人私聊通知。

边界：

- `services` 不 import telegram；
- `handlers/callbacks/review.py` 只保留 `applicant_text`、`notify_applicant`、`close_transit_message` 和回执文案；
- 审核消息删除、频道回执、私聊通知仍是 Telegram 适配；
- `ReviewService` 与 `ApplyService` 共用同一个 `get_applications()` 单例。

附带改进：

- 审核按钮重复点击 / 并发审核时，第二次返回 `already_processed`，不会重复改名单；
- 名单写入异常不再留下「状态已改、名单未改」的状态；
- 新增 `test/test_review_service.py`（9 个用例）和 `test/test_review.py`（8 个 handler 用例），全部通过。

## 6. 建议的推进顺序

### 阶段一：先让现状可靠（1～2 天）

1. 修测试：删除/重写过期用例，增加 `pytest-asyncio`，测试统一用 `tmp_path`。
2. 加管理员校验：`ADMIN_IDS` + 频道管理员双重校验。
3. 配置校验：启动时检查 `BOT_TOKEN`、分享频道、`TRANSIT_CHANNEL`，缺失直接拒绝启动或显式降级。
4. 修 `resolve_source` 空值、链接分派、`af;None`、作者临时目录残留。
5. 原子写 JSON，补 `__pycache__` 到 `.gitignore`，更新 `/start` 与 README。

### 阶段二：补齐核心产品能力（1 周）

1. 分享频道改为配置列表，逐频道发送并记录 `message_id`。
2. 白名单接入判定，明确 `黑名单 > 白名单 > 兽人名单 > 申请` 优先级。
3. 审核通过后自动把作品发到正式频道（或提供「放行」按钮）。
4. 暴露 `afb` 按钮，补「拒绝并拉黑」。
5. 申请卡片附带作品文件 / 预览，完善中转频道职责。
6. 申请冷却与防刷。

### 阶段三：内容识别与规模化（按需）

1. 标签 + 正文关键词过滤，作为人工审核前的辅助信号。
2. 翻译能力（独立于下载权限）。
3. 数据层迁移到 SQLite / PostgreSQL，加入任务队列（PTB `JobQueue` 或独立 worker）。
4. 连接池、重试、限流、进度提示、指标与告警。
5. Docker 化与部署文档。
