## 0. 这篇文档怎么用

遇到下面四种情况，直接跳到对应章节：

| 你的感受 | 看哪节 |
|---|---|
| 「我知道要做什么，但不知道从哪下手」 | 第 1 节 · 从最外层往里写 |
| 「我该改哪个文件？」 | 第 2 节 · 分层速查表 |
| 「这几层到底谁调谁？」 | 第 3 节 · 调用链逐层解剖 |
| 「点了按钮没反应 / 我要加个按钮」 | 第 3.3 节 · action 总表 |
| 「我好像忘了怎么写代码」 | 第 4 节 · 三个练习（30 分钟） |
| 「改完了，该跑什么？」 | 第 5.1 节 · 测试 ↔ 被测层 |

一句话结论：**写代码从最外层开始；抽象层只在「改到它」的时候才打开。**

### 0.1 先统一三个词：三套名单

项目里有**三个不同的作者名单**，名字都像「名单」，但业务含义完全不同。改代码前先认清，否则会像 `03` 文档第 7.3 节第 6 步说的那样「三套名单语义冲突」。

| 存储字段 | 数据文件 | 业务含义 | 是否生效 | 实测体量 |
|---|---|---|---|---|
| `ListManager.furrylist` | `data/furry_authors.json` | **兽人作者名单 → 决定能否下载** | ✅ 生效 | 47 KB |
| `ListManager.whitelist` | `data/white_authors.json` | 授权转载白名单 | ⚠️ **业务未使用** | 70 B（≈空） |
| `ListManager.blacklist` | `data/black_authors.json` | 黑名单 → 禁止下载 | ✅ 生效 | 394 B |

三者的关系：

- **`furrylist` 是唯一的放行依据**。判定在 `policy/author.py`：`blacklist` 拒下载且禁申请，`furrylist` 放行，其余一律 `needs_apply`。
- **`whitelist` 有读写方法、有存储，但产品决定暂不接入判定**——`AuthorPolicy` 明确不读它。
- 三者会**互相清理**：`ListManager.add_whitelist()` 会先 `blacklist.remove()`，`add_blacklist()` 会先 `whitelist.remove()`。所以它们是「互斥的两个标签」，不是独立的三份数据。

> **写作约定**：本文出现「兽人作者名单」= `furrylist`，「授权白名单」= `whitelist`，「黑名单」= `blacklist`。不要混用。

另外两个容易混的：

| 名称 | 位置 | 含义 |
|---|---|---|
| `furry_request` | `data/furry_request.json` | 用户的申请记录（数据键 `furry_request`），状态 `pending` / `approved` / `rejected` |
| `file_cache` | `data/files_cache.json` | Telegram `file_id` 缓存，默认 7 天（`FILE_CACHE_TTL_DAYS`） |

## 1. 唯一路径：从最外层往里写

### 1.1 先认领这三个症状

不是能力退化，是三个可以解释的现象：

| 症状 | 原因 |
|---|---|
| 打开 `services/` 就发懵，不知道从哪个方法开始 | **抽象倒挂**。你的抽象是「事后从能跑的 callback 里提炼」出来的（见 `03` 第 7.3 节第 4 / 4.5 / 4.6 / 4.7 步）。你练了四次「具体 → 抽象」，从没练过反方向 |
| 每个 `dataclass` 都看得懂，但拼不成一个功能 | **信息密度错位**。`DownloadArtifact` 有 11 个字段，一次调用只用其中 2~6 个。抽象层是给「读」和「改」用的，不是给「写」用的 |
| 以前改一行就有 bug 教你，现在怎么改都「对」 | **没有反馈**。层已经稳定，没有摩擦就没有信号，于是误以为「我什么都不懂了」 |

写代码需要的是「下一步」，抽象层只告诉你「允许什么」。这两件事不匹配，所以会卡。

### 1.2 五个台阶：什么时候才该抽一层

项目里现有的层，都是爬到第 3~5 级的产物。**加新功能时，只需要待在 1~2 级。**

| 级别 | 触发条件 | 动作 | 项目里的对应物 |
|---|---|---|---|
| **1 · 写死** | 刚有需求 | 在最外层硬编码，先把路径打通 | 直接在最外层调 `sources.fetch` / `sources.save`，不做任何编排 |
| **2 · 就地实现** | 逻辑只有一处用 | 逻辑就写在 handler 里，40 行也认 | `handlers/download.py` 里那堆文案分支 |
| **3 · 出现第二处调用** | 两处以上重复 | 才上提到 `services/xxx_service.py` | `download_service`（message handler 和 callback 都要用） |
| **4 · 需要替换 / 测试** | 想写单测 | 才做注入 `fetch_fn=` / `save_fn=` / `list_manager=` | `DownloadService.__init__` 的那组参数 |
| **5 · 出现第二个实现** | 真要换存储、换来源 | 才抽 `Protocol` / `ABC` | `NovelSource`（为 pixiv 预留）、`JsonStore`（4 个 Store 共用） |

**心法：写新功能时，假装这些层不存在。**

### 1.3 五步操作法

1. 打开**最外层**那个文件（`handlers/callbacks/xxx.py` 或 `handlers/xxx.py`）。
2. 用最丑的方式把功能写通：直接读 JSON、直接 `if`、直接 `print`。丑没关系，路径通了才有反馈。
3. 跑起来，看到效果。
4. 只问一句：「这一行是不是该问 `service` 要数据？」是 → 去 `service` 加**一个方法**，不在 `service` 里重构。
5. **停。** 不要顺手抽象。

### 1.4 反面案例：从抽象层开始写会怎样

> 「我要加一个下载计数。先去 `DownloadService` 加个 `record_count()` 吧。」

然后你会：

1. 纠结它该放在 `prepare` 前还是 `deliver` 后；
2. 纠结计数失败要不要抛异常、算不算下载成功；
3. 纠结要不要新的 `dataclass`、要不要改 `DownloadOutcome` 的字段；
4. 40 分钟过去，**一行能跑的东西都没有**，而且发现 `handlers/` 根本不需要这个数据；
5. 得出「我不会写代码了」的结论。

同一件事，从最外层开始写：

1. 先在 `handlers/callbacks/download.py` 里 `logger.info("下载 %s", artifact.item_id)`；
2. 跑一次，日志出来了，功能「通了」；
3. 真的需要落盘时，才去想存哪、存什么；
4. 于是你自然发现：该加的是 `storage/download_counter.py`（继承 `JsonStore`），不是 `DownloadService` 的方法。

**顺序不同，产出完全不同。** 抽象层不会告诉你怎么走，它只会在你走错时拦住你。

这张表解决 90% 的「我该动哪个文件」。

| 我想做的事 | 改哪里（按顺序） | 只写什么 | **别碰** |
|---|---|---|---|
| 改**常驻**提示文案 | `handlers/download.py`、`handlers/review.py`、`handlers/start.py` | `message.reply_text(...)` 的字符串 | `services/`、`storage/` |
| 改**callback** 提示文案 | `handlers/callbacks/*.py` | `reply(update, context, ...)` 的字符串 | 注意下面的「3 秒消失」坑 |
| 加一个按钮动作 | ① `keyboards.py` 造按钮 ② `handlers/callbacks/router.py` 的 `handlers` dict 注册 ③ 新建 `handlers/callbacks/xxx.py` | 一个 `async def xxx(update, context, *, data: str)` | `sources/`、`storage/` |

### 2.1 两个必知的坑

#### 坑 1：`reply()` 默认 3 秒后自动删消息

项目里有**两套**回复方式，行为不同：

| 写法 | 用在哪 | 行为 | 改文案后你会看到 |
|---|---|---|---|
| `update.message.reply_text(text)` / `message.reply_text(text)` | `handlers/download.py`、`handlers/start.py`、`handlers/review.py` | 消息常驻 | 文案一直挂在聊天里 |
| `reply(update, context, text, ...)` | 所有 `handlers/callbacks/*.py` | **默认 `delete_after=3` 秒后 `message.delete()`** | **文案闪一下就消失** |

`handlers/telegram/reply.py` 的签名是 `reply(..., delete_after: float = 3, **kwargs)`。

**所以**：你改了一个 callback 的提示文案，发出去 3 秒就没了 → 会误判成「没生效」或「代码没保存」。想让它留着，显式传 `delete_after=0`。

反过来，如果提示本来就该消失（「正在获取文件，请稍候……」），那 3 秒是**故意的**，别去改成常驻。

#### 坑 2：`services/__init__.py` 和 `handlers/__init__.py` 都有 `__all__`

两个包的 `__init__.py` 都用 `__all__` 显式导出。新增东西时**只加定义不加导出**，`from services import Xxx` 就会 `ImportError` / `NameError`。练习 B 会踩到这个坑，是故意的，让你记住它。

### 2.2 依赖红线：两条可自查的命令

速查表里那些「别碰」不是审美要求，而是**依赖方向**：

```text
handlers/  → 可 import telegram、services、policy、storage、sources
services/  → 可 import policy、sources、storage、infra、utils；不许 import telegram
policy/    → 可 import storage（只读名单）、utils；不许 import services
storage/   → 可 import infra、utils；不许 import services
sources/   → 可 import infra、utils；不许 import services
```

实测现状（2026-11-11）：`telegram` 只被 `handlers/` 下 11 个文件 import，其余目录 **0 处**。

```powershell
# 红线自查 1：这条命令应该【没有任何输出】。若有输出，说明那个文件越界 import 了 telegram
Select-String -Path (Get-ChildItem -Recurse -Filter *.py -Path services,policy,sources,storage,infra,utils | % FullName) `
  -Pattern "^from telegram|^import telegram" | % { $_.Path }

# 红线自查 2：下层不许反向 import 上层（同样应该没有任何输出）
Select-String -Path (Get-ChildItem -Recurse -Filter *.py -Path services,policy,sources,storage | % FullName) `
  -Pattern "^from handlers|^import handlers"
```

> 2026-11-11 实测：两条命令都是**空输出**，说明当前依赖方向是干净的。**这就是你重构时最可靠的护栏。**

**为什么这条最重要**：它让 `services/` 可以在没有 Telegram 环境的情况下被单测（`test_download_service.py` 就是这么跑的），也让将来的你换掉 Telegram 框架时不用重写业务逻辑。**这是「分层」唯一能兑现的收益。**

## 3. 一条真实调用链的逐层解剖

场景：用户在私聊发一个 Linpx 单篇链接，点「下载单篇」，收到一个 `txt`。

每一层都标了**「想验证这层，就改这里」**——这是恢复手感最快的方法：不看类定义，看数据流。

> 本节**不写行号**（行号会漂）。需要具体行号时，跑 3.4 节的命令现取。

```text
① 用户私聊发链接
   handlers/download.py · download()
     └─ service.inspect_text(text)
        ← 改这行的 reply_text，能立刻确认「最外层」是谁

② DownloadService.inspect_text              services/download_service.py
     └─ get_url(text)                       utils/links.py
     └─ inspect_link()                      services/download_service.py
          └─ _resolve_source(link)          sources/__init__.py · resolve_source()
          └─ _fetch(link)                   sources/__init__.py · fetch()
               └─ LinpxSource.fetch_novel() sources/linpx/
          └─ 返回 DownloadOffer
        ← 想验证「解析对不对」，在这里 logger.info("offer=%s", offer)

③ DownloadService.check_access(offer)        services/download_service.py
     └─ AuthorPolicy.check(author_id)       policy/author.py
          └─ ListManager.is_blacklisted()   storage/author_list.py
          └─ ListManager.is_furryauthor()   storage/author_list.py
     └─ 返回 AuthorAccess(status=...)
        ← 想验证「名单生效没」，在这里 logger.info("access=%s", access)

④ handler 用 offer + access 渲染键盘         handlers/download.py
     └─ keyboards.py 的 down_novel_keyboard / down_novel_series_keyboard / ...

⑤ 用户点按钮 → CallbackQueryHandler
   handlers/callbacks/router.py · button_callback()
     └─ action, _, rest = data.partition(";")      data 形如 "dn;https://..."
     └─ handlers dict 查表 → "dn" → download        （action 全集见 3.3）
     └─ handlers/callbacks/download.py · download()
          └─ service.deliver(action, link, upload=send)
                ← upload 是**注入**的闭包：Telegram 相关的一切都在这里，
                  service 里不 import telegram（红线见 2.2）

⑥ DownloadService.prepare                   services/download_service.py
     └─ self.cache.get_valid(cache_key)     storage/file_cache.py
     └─ 未命中 → _fetch → _save → DownloadArtifact

⑦ upload(artifact) → upload_file()          handlers/telegram/upload.py
     └─ 有 file_id 就复用，否则 send_document 并写缓存

⑧ deliver 的 finally 删本地文件               services/download_service.py
```

### 3.1 调试练习（5 分钟，效果最明显）

在 ② 加 `logger.info("offer=%s", offer)`，在 ③ 加 `logger.info("access=%s", access)`，然后发一个链接、点一下下载。

你会第一次「看见」抽象层——因为你在看**数据流**，不是在看类定义。

> 这就是手感的来源：不是理解架构，而是能预测下一行输出。

### 5.4 缩进：一律 Tab，`.editorconfig` 定调 + 一个测试锁死

本项目所有 `.py` 用 **Tab 缩进（Tab = 4 列）**，不用空格缩进代码块。保证这件事只需要两样东西，**不需要提交 `.idea/`，也不需要任何额外 IDE 配置**：

| 层 | 文件 | 干的事 |
|---|---|---|

三个必须知道的行为：

1. **PyCharm 里只有两个开关要管**：`Settings → Editor → Code Style → Enable EditorConfig support` 必须**勾上**（默认勾选，这是 `.editorconfig` 的唯一入口）；`Detect and use existing file indents for editing` 必须**取消**。后者会按文件现有缩进覆盖配置，判断方法是看编辑器右下角：显示 `4 spaces` 就说明它在生效，点它切回 `Tab (4)`。
2. **docstring 里的两格缩进不算违规**。`test_style.py` 走 `tokenize`，只看真正产生 token 的代码行，所以 `  - 这句话` 这种文档排版随便写。
3. **`__pycache__/` 已在 `.gitignore` 里**，跑完测试不会再冒出未跟踪目录；如果之前漏提交过，`git rm -r --cached __pycache__` 清一次索引即可。
